# 知识库 03：工具链与构建系统

> 归属阶段：阶段 5。编译器/构建系统/包管理器三角色、平台选择、完整工具清单、跨平台推荐。

## 4.1 三个角色（不要混为一谈）

- 编译器（compiler）：把源码翻译成目标代码。GCC / Clang / MSVC。
- 构建系统（build system）：CMake 是「元构建系统」，描述怎么构建，再生成底层构建文件；
  Ninja / Make / MSBuild 是「底层执行者」，真正跑编译命令。
- 包管理器（package manager）：下载/编译第三方依赖。Conan / vcpkg（Windows）/ apt·pacman（Linux）/ Homebrew（macOS）。

你项目里已经正确用了「MinGW clang + CMake + Ninja」这套组合，只是包管理（conan）没接上。

## 4.2 正确的组合（Windows 主流）

    1. MSVC + CMake + Ninja + vcpkg        微软全家桶，VSCode/VS 集成最好，最主流
    2. MinGW GCC + CMake + Ninja + Conan   你现在的方向，开源、接近 Linux 生态，Conan 最稳
    3. MinGW Clang + CMake + Ninja + Conan clang 前端 + GNU 后端（见第6节的风险说明）

要点：
- generator 用 Ninja（快、并行、输出清爽）；
- Conan 和 vcpkg 二选一，别混用；
- 同一套 ABI（libstdc++）下，g++ 和 clang++ 编译出的库可以互相链接（MinGW 两者都用 libstdc++）。

## 4.3 平台选择

- Windows：MSVC（官方、集成好、闭源）或 MinGW（GCC/Clang，开源、贴近 Linux）；
- Linux：GCC 或 Clang + CMake + Ninja + Conan/vcpkg/系统包；
- macOS：Apple Clang + CMake + Ninja + Homebrew/Conan。

## 授人以渔：学会任何 CLI 工具的四步法

1. 心智模型：这工具解决什么问题、核心对象是什么（conan=依赖、git=版本、cmake=构建配置）；
2. 命令骨架：程序 子命令 位置参数 选项——所有 CLI 工具通用；
3. 逐参数拆解：每个选项控制哪个行为；命令行参数优先级高于 profile/配置文件；
4. 需求映射：需求 → 参数（用 --help 定位哪个选项控制这个行为）。

查文档顺序：工具自带的 --help 优先 → 官方文档按需求关键词搜索 → 最后才搜博客。
工具自带信息永远比二手博客可靠。

### 示范：conan install 逐参数拆解

    conan install . --build=missing -pr:h=mingw-gcc -s build_type=Debug
     └程序  └子命令 └位置参数     └选项=值        └选项=值          └选项=值

    conan .............. 程序名
    install ............ 子命令：安装依赖（解析 conanfile → 下载/编译 → 生成配置）
    . ................. 位置参数：项目目录（含 conanfile.txt），. = 当前目录
    --build=missing .... 构建策略：只在缓存缺失时从源码编译
                        （never=永不 / always=总是 / raylib=只编 raylib）
    -pr:h=mingw-gcc .... -pr=profile，:h=host 目标环境，mingw-gcc=配置名
                        （conan 区分 host 运行环境 / build 构建环境，单机两者相同）
    -s build_type=Debug  -s=settings，覆盖 profile 里的 build_type（命令行优先级更高）

需求映射速查：换 Release → -s build_type=Release；换 profile → -pr:h=名字；
强制重编某包 → --build=包名；看缓存/远程有什么 → conan list / conan search。



## 单配置 vs 多配置（generator 的两种组织方式）

构建类型（Debug/Release）是「要编什么」；单/多配置是「generator 怎么管理构建类型」。

单配置（Ninja / Unix Makefiles）：一次 configure 只生成一种构建类型

    cmake --preset conan-debug   → build/Debug/   （preset 里 CMAKE_BUILD_TYPE=Debug）
    cmake --preset conan-release → build/Release/ （preset 里 CMAKE_BUILD_TYPE=Release）
    换构建类型 = 换目录重新 configure；CMAKE_BUILD_TYPE 是选择方式

多配置（Visual Studio / Xcode）：一次 configure 包含所有类型

    cmake --preset conan-default → build/（含 Debug/、Release/ 子目录）
    编译时选：cmake --build . --config Release；CMAKE_BUILD_TYPE 被忽略

关键：单/多配置由 generator 决定，不是 preset 决定；
preset 里的 CMAKE_BUILD_TYPE 只在单配置下有意义。
Conan preset 命名：单配置 → conan-{build_type}（conan-debug），多配置 → conan-default。



## 工具探索闭环（跨工具：需求 → 定位 → 探索 → 查档）

有了新需求时：
    1. 按职责定位到工具链中的某个工具（依赖→conan，构建→cmake，版本→git）；
    2. 探索有没有类似命令（--help 或猜命令名）；
    3. 有 → 官网查文档精读；
    4. 没有 → 重新定位工具；
    5. 定位不出来 → 社区/帖子兜底。

这是「四步法」的跨工具版本：四步法学单个工具，闭环在工具之间导航。

配套判断：工具链已完整时，剩下的是「深入用」而非「加工具」；
同类工具切换（gcc↔clang、conan↔vcpkg）靠抽象层（profile/preset）隔离差异，切换成本低——
抽象层的价值 = 单一真相来源 + 隔离变化。
